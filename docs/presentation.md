# Presentation and subject

A reply is text, written for someone to read. A user interface usually wants
more than that: which record the turn is about, and what to render for it —
a card, a table row, a confirmation panel — without scraping the sentence a
model wrote. Presentation directives are that second channel: a procedure
declares, once, what it wants shown at a named moment, and the engine fills
that declaration from what actually happened this turn. Nothing about it is
generated by a model, and nothing about it is optional plumbing a UI can
ignore — it is the only place the exact data behind a reply is available as
data.

This document is for building something against the HTTP API: the binding
grammar, the precedence rules, and the shape a response carries. The code is
`src/oska/engine/presentation.py`, `src/oska/engine/subject.py` and
`src/oska/ontology/naming.py`; the declarations are fields on
`SkillFrontmatter` in `src/oska/contracts/skill.py`.

## Declaring a directive

A runbook or a composite — never an entity — may declare `presentation`, one
entry per named moment:

```yaml
subject:
  entity: entity.service
  cardinality: one
  joins: focus
presentation:
  on_selection:
    view: service_selected
    bind:
      service: $selection
  on_verified_write:
    view: service_restarted
    bind:
      service: $receipt.service
      receipt: $receipt.receipt_id
      verification: $receipt.verification
```

(`examples/ops/skills/runbook/service_restart/v1/skill.md`.)

A moment is one of `on_verified_write`, `on_selection`, `on_results`,
`on_single_result`, `on_completion` — tried in that fixed order for every
procedure that ran this turn. The first moment that the procedure both
declares and the turn's evidence actually reaches wins; a procedure emits at
most one directive per turn. `on_verified_write` outranks every other moment
whenever a verified write happened, because a confirmed write is the strongest
thing a turn can say — see [Precedence](#precedence) below. `on_completion`
is reached only when the goal the procedure belongs to finished in this turn
and every write the turn performed or found for it was confirmed by its
read-back; a goal still waiting on a step, or carrying a write that was not
verified, never reaches it.

`view` is a name your UI switches on — the runtime does not interpret it, and
neither does anything in `src/oska`. `bind` is a map of field name to a
binding expression, resolved against evidence gathered from this turn alone.

An entity, in turn, declares how its records are named and compared, never
how they are shown at a moment:

```yaml
noun: alert
plural: alerts
display_fields: [id, service, rule, state]
comparable_fields: [state, service]
```

(`examples/ops/skills/entity/alert/v1/skill.md`.) `noun` defaults to the
entity's short id segment (`entity.alert` → `alert`) and `plural` to `noun`
plus `s` when not given. `display_fields` are what a person is taken to mean
when they refer to a record by something other than its identifier — "the one
in finance", "the checkout one" — and `comparable_fields` are what a
comparative question ("which one is failing") may refine on. Both are read by
`oska.ontology.naming`, and both apply only to `type: entity` skills; a
`runbook` or `composite` declaring them is a validation error, the same way an
entity declaring `presentation` or `subject` is.

## The binding grammar

A `bind` value is a plain string copied verbatim unless it starts with `$`,
in which case it is one of four forms:

| Binding | Resolves to |
| --- | --- |
| `$items.<field>` | That field, as a list, over every record the evidence's read returned |
| `$item.<field>` | That field of the one record read — only valid when exactly one came back |
| `$selection` | The identifier of the record the focus resolved to, no field |
| `$receipt.<field>` | One of `receipt_id`, `operation`, `integration_id`, `verification`, `status`, or a key inside the verified write's payload |

What a person typed is not among them. A value somebody gave is evidence only
once a write carried it and its read-back confirmed it, and then it is
reached as `$receipt.<field>`; a binding written as `$inputs.<field>` is
refused at validation time, `presentation_unverified_input` — echoing what a
person typed is not evidence, whatever it happens to agree with.

`service: $receipt.service` above resolves against the payload of the receipt
the write produced — the same payload a person approved, because the receipt
is the record of what was actually sent. Nothing here is text a model wrote:
every binding resolves against typed evidence assembled from this turn's
outcomes, never from the reply.

## Evidence, and what makes a directive disappear

Evidence is assembled only from what this turn's plan actually produced:
successful reads (`outcome.kind == "read"`), a receipt whose verification is
`verified` — not merely `executed` — the record the focus resolved to when
the procedure joined it, and the inputs the goal collected. No model text is
evidence, and nothing outside this turn is either; a directive says what this
turn showed, not what the runtime remembers.

A binding the evidence cannot answer — `$item.<field>` when two records came
back, `$receipt.<field>` on a write that was not verified, `$selection` with
nothing in focus — drops the **whole directive**, not just the one field. A
procedure whose moment cannot be filled says nothing rather than something
half true: there is no partial directive, and a UI never has to guard against
a directive with a hole in it.

A directive is read-only by construction. Nothing in the engine consumes a
`Directive` back as input to a decision; it is assembled after the plan has
already run, and it never reaches the planner, the policy engine or a
connector.

## Precedence

**Moment order is fixed and total.** `on_verified_write`, `on_selection`,
`on_results`, `on_single_result`, `on_completion`, always in that order. When
several are declared and several are reachable, the earliest one in this list
wins — a turn that both selected a record and verified a write against it
reports the write, because that is the stronger fact.

**Every procedure that ran gets its own directive.** There is no precedence
between procedures: a turn that hydrated more than one runbook — the steps of
a composite — can carry more than one directive, one per procedure, in the
order those procedures ran.

**There is no entity-versus-runbook conflict**, because only a runbook or a
composite may declare `presentation` at all. An entity's `noun`,
`display_fields` and `comparable_fields` inform how a runbook's bindings and
the subject engine read records; they never emit a directive of their own.

## Subject: what the conversation is about

Presentation says what to show; subject says what "it" refers to next. Every
turn updates `focus` on the session: the entity, the identifiers shown, a
cardinality of `one` or `many`, and where it came from. A read or a verified
write updates focus to what it showed; an unverified write updates nothing,
because an unconfirmed write is not evidence of state.

A procedure that declares `subject.joins: focus` is offered the identifier of
whatever is in focus as a collected input — not something the model invented,
something the session already showed. Resolution, in order:

1. **A literal identifier mentioned in the turn** wins outright.
2. **The record whose `display_fields` overlap the turn's wording best**, and
   only when that overlap strictly beats the record currently in focus — a
   tie changes nothing, so "the one in finance" cannot flip a decision by
   an equally good coincidence.
3. **Standing focus**, when neither of the above applies.

A procedure declaring `cardinality: one` never guesses a single record out of
a list in focus — "silence it" with three alerts on the table asks which one,
it does not pick. That is what makes `restart it`, after a health check
already showed one service, resolve without a question:

```sh
$ oska run --skills examples/ops/skills --session demo \
    --provider scripted --script examples/ops/scenarios/27_subject_from_what_was_shown.json
```

Turn one, "how is the search service doing in staging", shows one service and
emits a directive at `on_single_result`. Turn two, "restart it", never names a
service; the plan carries `{"service": "search"}` anyway, taken from focus,
and the approval prints the exact payload as always. Nothing about the write
path changes because of this — a value the focus supplied is still shown,
still frozen on its hash, still subject to approval, exactly like a value the
model would otherwise have had to ask for.

### Comparatives

When focus holds several records (`cardinality: many`) and a person asks a
comparative question, the engine looks at `comparable_fields` the entity
declares and the fields the read's own input schema accepts, and offers a
refinement only on the ones the shown records actually differ on — never on
one where they all agree, and never on a free-text field with no enumerable
values, even if it is listed as comparable. An enum field is offered as the
subset of values actually present among the shown records; a numeric field is
offered with the minimum and maximum actually shown, inside the field's
declared bounds. This is what "grounded in the rows on screen" means in
practice: the question a UI can ask next is computed from what was shown, not
from the schema alone.

## The HTTP shape

`POST /sessions/{session_id}/turns` and
`POST /domains/{domain}/sessions/{session_id}/turns` return a `TurnResult`:

```json
{
  "reply": "search is running in staging on version 0.8.2 with 2 replicas.",
  "outcomes": [ { "kind": "read", "...": "..." } ],
  "pending": null,
  "events": [ { "kind": "reply", "data": { "subject": { "...": "..." }, "directives": [ "..." ] } } ],
  "directives": [
    {
      "procedure": "runbook.service_health",
      "moment": "on_single_result",
      "view": "service_status",
      "fields": {
        "service": "search",
        "environment": "staging",
        "status": "running",
        "version": "0.8.2"
      }
    }
  ]
}
```

`directives` is a top-level list of `Directive` (`procedure`, `moment`,
`view`, `fields`) — read it from here. The same data is duplicated inside the
`data` object of the `reply`-kind `AuditEvent` in `events`, together with
`subject` (`procedures`, `source`, `entity`, `identifiers`): that is currently
the only place subject/focus information appears in a response, so a client
that wants to know what the conversation is about, rather than only what to
render, reads `events` for the entry whose `kind` is `"reply"`. There is no
separate endpoint for a session's current focus outside a turn reply.

`GET /domains/{domain}/capabilities` and `GET /capabilities` do not carry
presentation information — they answer what a domain can do, in words, not
what a given turn showed.

## Enabling it

Presentation is off unless the engine is built with it enabled — `presentation`
on `build_engine()` in `src/oska/engine/factory.py`, `False` by default; a
turn run with it off never emits a `directives` list, however a procedure is
declared. Three places set it:

- **A platform domain.** `DomainSpec.presentation` in `platform.yaml`,
  `false` unless a domain turns it on — see
  [docs/packs-and-platforms.md](packs-and-platforms.md).
- **A scenario.** A scenario file may carry a top-level `"presentation": true`,
  and `oska conform` then builds that scenario's engine with it on, the same
  way a domain that enables it builds its own — see
  [docs/conformance.md](conformance.md#turns).
- **A plain catalog you serve yourself.** A single-catalog deployment run
  through `oska serve --skills ...` or `oska run --skills ...`, with no
  platform manifest, does not turn presentation on today — that path calls
  `build_engine()` with the default. A team wiring the library directly turns
  it on by passing `presentation=True` to `build_engine()`.
